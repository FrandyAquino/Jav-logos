# Workspace performance and quit-path baseline

Measured 2026-11-27. Measurement/diagnosis only; no production refactor, no commit, no dependency changes. The only production-source addition from this investigation is a `#[cfg(test)]` module declaration in `storage.rs`. Other concurrent working-tree edits belong to their authors, including directed refinement. Reserved paste/drop files were not edited.

## Reproduce

From the repository root, with existing dependencies/toolchains:

```sh
node scripts/performance-baseline.mjs
```

This creates deterministic fixtures under the OS temporary directory, runs the actual Rust `Store` in release mode and opt-in Vitest diagnostics sequentially, prints JSON containing every sample, and removes fixtures/databases/assets in `finally`. It never opens the user's workspace or starts an app/server. The first run compiles the release test target. Normal `npm test` searches only `src`; normal `cargo test` skips the ignored diagnostic. No packages or models are needed beyond this checkout's existing dependencies. `--frontend-only` is an optional fast refresh that regenerates the same fixtures and runs only the frontend diagnostics; the default command runs both layers. Each stage now prints its own start/end fingerprints to make concurrent edits visible. Killing the runner with SIGKILL can leave its temporary directory; remove only the named `javlogos-perf-*` directory after its process has exited.

Retained samples, source fingerprints and machine metadata: [performance-baseline-results.json](performance-baseline-results.json). Timings are medians of five observations, not percentile estimates or release certification. Source fingerprints before/after the final run identify concurrent-source drift. The full-run fingerprints changed in `storage.rs`, `use-studio.ts` and `schema.ts` during concurrent refinement work. Native numbers describe the release test binary compiled at the beginning of that run. Frontend numbers were refreshed separately after those edits with identical start/end source fingerprints; both receipts are retained. These are separate layer measurements, not one immutable native/WebKit acceptance run. Git base: `6a6b6fb51229dca879a8ae869b9074ca7d67cc7d`; the measured checkout includes concurrent uncommitted refinement work.

Host verified with `sw_vers`, `system_profiler SPHardwareDataType`, `node --version`, `rustc --version`: macOS 27.0.1 (26A434), Apple M5, 10 cores (4 performance/6 efficiency), 24 GB RAM, Node 24.22.2, Rust 1.96.0, aarch64-apple-darwin. The machine was not reserved or made thermally idle; these are warm-cache local diagnostics, not machine-cold startup. Fixture generation, compilation, parsing initial fixtures, opening the Store and cloning Rust inputs are outside operation timers. Seed timings include writing all new assets and durable filesystem operations. Load timers include new connection, SQLite query, validation and asset hydration; they exclude Tauri response serialization and WebKit delivery. Save timers consume owned inputs, validate, serialize, transact, process every asset and commit; they exclude renderer validation and Tauri request deserialization.

## Fixtures and scope

Paired sizes are 10 brands/100 concepts, 50/500, 200/2,000. Brands are independent roots. Every concept has a unique valid 512×512 RGB PNG, 25-path SVG, editable document and three document-only versions. Every fourth concept also references its raster; every tenth has a cutout with those same bytes. Asset deduplication therefore works within a concept, but independent concepts have distinct content hashes. PNGs contain a synthetic textured gradient and geometric mark, approximately 18.6 kB compressed; unique PNG `tEXt` identifiers keep file identity distinct. This is a reproducible small-logo workload, not generated FLUX imagery or a model-quality benchmark. Larger/noisier real PNGs reach the byte cap much earlier.

Rust uses five fresh temporary Stores per size. Save-one changes one name; save-all changes every document's rotation; delete removes one concept. All remain full-workspace writes. A stale revision is rejected with the complete original payload. Assets are read back and a raster compared with its source. Each run advances the backup after deletion, computes the union of both DB snapshots' asset references, injects a SQLite UPDATE-abort trigger after asset writes, verifies the persisted revision is unchanged, and counts new orphan files. Logical file lengths are reported, not APFS allocated blocks or cumulative write amplification.

TypeScript measures real JSON parse/stringify/structuredClone/Zod validation and real `useStudio` metadata edit, version-save and deletion actions. Only the desktop boundary is mocked: it validates and serializes the same `{snapshot,expectedRevision}` arguments, then acknowledges a revision. It does not measure native IPC latency or simulate filesystem durability. Store-operation timings include React hook notifications and the boundary serialization, with the visual workspace unmounted. The gallery test mounts real `CreativeCanvas`, `BrandSidebar`, `ConceptCard` and `ConceptArtwork`, wraps artwork only to count renders, uses React Profiler, and changes the real store prompt. For the gallery stress case all concepts are assigned to the selected brand without changing count/assets; the distributed fixture normally displays only ten per brand. This is jsdom/development React: no CSS layout, painting, real image decoding, GPU work or WebKit runtime memory.

## Risk A: end-to-end storage and memory trace

1. `use-studio.ts:188` serializes operations through `writeQueue`. Each operation transforms the current workspace, Zod-parses the entire result, publishes “Saving…”, calls the desktop adapter and replaces the entire workspace after acknowledgment. `desktop.ts:60` parses the whole workspace again and passes every concept and its data URLs to `invoke`. A name edit, version save and delete therefore have almost identical payload sizes. Zod constructs new nested objects/arrays; JavaScript engines can share immutable string backing stores, so object cloning is not proof of one physical raster allocation per object.
2. `lib.rs:29` and `lib.rs:37` deserialize/return full typed snapshots and move work to `spawn_blocking`. `storage.rs:155` validates every field and serializes the entire hydrated input into a temporary byte vector to check 128 MiB. The vector is retained in scope during subsequent work. Only then does it open a connection, acquire `BEGIN IMMEDIATE` and read the single-row revision. Stale rejection avoids asset writes, but still pays validation and full input serialization; measured separately above. Revision mismatch remains atomically checked inside the transaction.
3. `storage.rs:181` iterates every PNG, reference, cutout and current refinement-before PNG, decodes base64, hashes bytes and checks the content-addressed destination even if unchanged. SVGs are hashed on every save too. Files already present are reused, but processing/IPC costs remain. New files are fsynced and atomically persisted, including parent-directory sync (`storage.rs:214`, `storage.rs:268`). Filesystem writes happen while SQLite's write transaction is held. They do not roll back when SQL fails. A large first save can hold that lock longer than the five-second busy timeout of another writer; a second window/process can therefore fail instead of waiting for completion. Concurrent-writer latency was not benchmarked here.
4. `storage.rs:207` serializes metadata and `asset:png:`/`asset:svg:` tokens to the singleton SQLite row, copies the old row into `workspace_backup`, and commits. SQLite does **not** contain the base64 PNGs. No per-concept rows, search queries or concept indexes exist: the integer primary key handles `WHERE id=1`; adding a concept index cannot optimize this schema. `storage.rs:33` enables WAL; connections set synchronous FULL and a 5-second busy timeout. One immediate transaction performs revision SELECT, backup INSERT/REPLACE and snapshot UPSERT per save. Connections open/close per operation; last-close/checkpoint and lock contention belong to the measured Store calls, not a pooled-connection design.
5. `storage.rs:76` reads the whole metadata string, deserializes, validates stored references, then reads/checksums/base64-encodes every asset on load and validates again. The same hash in reference/cutout is re-read for each field; there is no read cache. IPC response serialization, JS parsing/Zod and SVG sanitization (`desktop.ts:42`) follow hydration and are additional costs not measured by the Rust timer. Startup never lazily requests a selected brand or thumbnail.

### Capacity and memory

- Expanded PNG strings are 4/3 of compressed image bytes plus the data-URL prefix. Counting raster/reference/cutout separately, this fixture carries 1.35 raster fields per concept plus SVG/documents/versions. Content-addressed deduplication reduces disk bytes, not expanded payload bytes. At 2,000 concepts the persisted DB metadata is only a few MiB while every save transports the much larger expanded snapshot.
- `types.ts:87` versions contain only documents; they do **not** copy raster/trace/reference assets. Forty undo documents per active history (up to ten concepts, `use-studio.ts:121`) are session-only. A restored version keeps using the concept's current asset, so retracing replaces its asset for all document versions. A version save grows metadata but creates no new asset file. New cutout derivatives clone their source concept and keep original raster/reference/trace fields (`use-studio.ts:863`, `saveCutout`); they can repeat those strings in later payloads despite disk deduplication. Pending generation/recovery arrays and composer references can retain additional live strings. Current concurrent refinement adds a before-image field to the same native PNG traversal; the benchmark does not populate it.
- At 2,000 decoded 512×512 RGBA images, one decoded image per concept alone would require 2,000 MiB (about 1.95 GiB), independent of compressed/data-URL size. This is a capacity calculation, **not** measured WebKit RSS or a guarantee that every image decodes simultaneously. Main art, generated SVG image sources, thumbnails, compositor surfaces and duplicate decodes can add memory; browsers may cache/share or evict them. `ConceptArtwork` has no `loading="lazy"`/`decoding` policy or thumbnail derivative. Raster mode reuses a data URL; trace mode additionally percent-encodes SVG; composed image/trace mode embeds assets into SVG strings (`presentation/ui.tsx:12`, `infrastructure/composition.ts`, domain vector rendering).
- Node `memoryObservation` in raw results is a before/after heap/RSS observation while microbench temporary strings/clones are allocated. There is no forced-GC isolation, allocator attribution or native-webview memory sampling; do not call the delta retained workspace memory or extrapolate it linearly.
- The 128 MiB cap is on expanded JSON bytes, not concept count. With 256 KiB compressed PNGs and the same 1.35 raster-field ratio, raster data alone consumes about 461 KiB/concept; the cap is reached before roughly 285 concepts, allowing fewer after SVG/metadata. This is arithmetic, not a measured real-model workload. Count limits are separately 1,000 brands/2,000 concepts (`model.rs:163`).
- **New reproduced correctness edge:** save checks serialized expanded JSON; load starts with the stored JSON length and then adds full hydrated asset lengths without subtracting stored asset-token lengths (`storage.rs:113`). The opt-in boundary probe pads valid SVG fields below individual limits, saves just below 128 MiB, then cannot load it (`WORKSPACE_TOO_LARGE`). It deliberately stresses the accounting boundary, not typical logo complexity. The accepted save was 134,216,704 bytes, only 1,024 bytes below the 134,217,728-byte cap. Fix this before raising workspace limits.

### Assets and safe GC

Confirmed: there is no GC. Save failures after one or more successful `write_asset` calls can orphan those files despite a DB rollback. Stale revision rejection happens before asset writes and does not itself create orphans. Concept deletion leaves its files, initially still required by the backup; one further successful save advances that backup and makes uniquely owned deleted assets collectible. Retracing/replacing raster/reference/cutout or before-images leaves superseded files once neither snapshot references them. Version-document churn alone creates no asset files. Process death between file persistence and commit has the same orphan possibility. Atomic-write temporary files normally clean up on drop; process death can leave temporary files, which require a separate conservative policy.

Measured deletion of one uniquely owned raster+SVG left two files unreferenced after advancing the backup, at every size. An injected SQL failure added one new orphan SVG and left the persisted revision intact at every size. The diagnostic marks **both** `workspace` and `workspace_backup`; marking only the latest snapshot would destroy backup recoverability.

Recommended initial GC contract, for the follow-up design:

- Native authority only; enumerate the fixed app-data assets directory, accept only known hash/extension names, reject symlinks/unknown entries and retain corrupt DBs untouched. Mark all assets in both snapshots, including optional refinement-before assets and every future asset-bearing field. Reuse one audited reference traversal, not a separately maintained field list.
- Start with an exclusive maintenance window, no in-flight save, generation-result publication, import/export or asset readers. Coordinate across windows **and processes**; an in-process mutex alone is insufficient. Existing `BEGIN IMMEDIATE` during save provides a useful writer ordering primitive, but live readers and staged assets also need protection. Keep an explicit staging/lease set and take the same maintenance lock around asset publication, mark and sweep. Never sweep files of an active or not-yet-committed save.
- Retain unmarked files for a configurable grace interval (24 hours is a proposed initial value, not an established requirement). Under the lock, re-read both DB roots immediately before quarantine; use atomic quarantine and a second grace period before final unlink. A grace interval alone is not a proof against races. Initial GC should stay offline/manual until fault tests cover save/GC interleavings, backup recovery, crash/staging cleanup, disk-full, corrupted assets and two instances.
- Report reclaimable bytes before deletion. The baseline's injected-failure/deletion counts must become zero collectible leaks only after GC has run and grace expires; live/backup/staged assets must survive and re-open with matching hashes. Never include independently exported user files in GC.

### React work

`useStudio()` calls the Zustand hook without a selector (`use-studio.ts:1216`), so prompt, status, provider health, generation progress and workspace edits notify every mounted consumer. Progress polling is every 500 ms (`generation-monitor.ts:18`). The returned studio object is new; components receive that whole object. `CreativeCanvas` filters all concepts on every render (`creative-canvas.ts:83`); both gallery and strip map all selected-brand concepts (`:261`, `:382`). `ConceptCard` and `ConceptArtwork` are not memoized; callbacks are allocated per card. `BrandSidebar` recomputes pinned/visible lists (`brand-sidebar.ts:77`) and renders all matching rows with parent lookups, without virtualization. No list is windowed. Derived selection uses linear `.find` over the whole arrays; hierarchy validation also walks every brand ancestry, so the flat-brand benchmark does not bound deep-tree costs.

The measured concentrated-gallery prompt render count proves unchanged images still traverse artwork components on each prompt change. It does not prove new image decodes occur each time. There is no browser/native paint benchmark here; image decoding/texture pressure, sidebar search, drag performance, deep hierarchies, 100 large-path versions and export throughput remain unmeasured workload extensions. The real component tree and sidebar are included in profiler totals, but per-sidebar-only timings are not isolated.

## Risk B: quit trace

There is no debounced persistence timer in the current production store. Text fields retain a local draft and commit on blur/Enter (`property-fields.tsx:162`); range fields commit on pointer/key release/blur (`:25`); colors commit on Apply. Treat “pending debounced save” as two distinct cases: an uncommitted control draft and an already queued/in-flight `persist`. Generation-monitor timers are unrelated to saving.

`prevent_exit()` **is** used, but only for active registered generation workers. It does not send `CloseRequested`, invoke `shouldBlock`, flush `writeQueue`, persist recovery, or examine JS `busy`. A blocked window close invokes `fail()`, which causes additional renders. Once a failed ordinary edit leaves the queue, `pendingWrites` becomes zero; `writeError` alone is not part of the close predicate. The old saved concept remains in state, while a control's local draft may disappear on close. The generation recovery guarantee applies specifically to `pendingConcepts`, not every failed edit.

Worker evidence: jobs are registered before async `generate` and removed by `JobRegistration::drop` (`worker.rs:99`, `:114`). `cancel_all` signals the watch senders (`:213`). Unix subprocesses start in a new process group (`:423`); on cancellation/timeout `terminate` sends group SIGTERM, waits up to 12 seconds in 50 ms intervals, SIGKILLs the original group ID, and waits for the child (`:350`, `:467`). This retains the original group even if its leader exits. Windows uses taskkill `/T /F`, unrun here. `lib.rs`'s outer registry-poll task has no global timeout and repeated exit requests can spawn multiple drain tasks. Health/vectorization use the generic worker runner but are not registered in `WorkerManager.jobs`; its quit wait therefore does not cover all subprocess work. `kill_on_drop` is not an OS process-death descendant-cleanup certificate.

The opt-in `quit-path.test.tsx` executes the real frontend predicate with deferred save/generation mocks: blurring an uncommitted real TextField synchronously queues a save and blocks, pending save blocks, acknowledged save unblocks, in-flight generation blocks, failed result persistence retains one pending concept and blocks, exporting recovery permits close while retaining the in-memory batch. This proves predicate state transitions, **not delivery of native close/quit events**, and intentionally cannot certify Cmd+Q or Dock Quit.
